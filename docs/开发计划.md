## 功能立项标准

一项新功能必须同时满足以下条件，否则不进入开发：

1. 解决本人已经出现的真实问题，而不是为了增加功能数量。
2. 有明确、可靠的数据来源，不从自由文本或缺失数据中推测结果。
3. 不与现有功能表达同一批信息；如果两个视图差异不明显，只保留更清晰的一种。
4. 能说明使用频率和完成后的实际收益。
5. 可以通过局部增量实现，不破坏已确认的布局、配色和交互。
6. 涉及删除、覆盖或自动计算时，必须提供确认、校验或恢复路径。

## 约束与原则

- 坚持保护性开发：新样式和新功能必须限定作用范围，优先局部增量修改，不以全局覆盖破坏已确认的视觉与交互。
- 修改前确认相关模块的既有设计；非用户明确要求，不改变其他模块的配色、布局、尺寸或行为。
- 不为了完成路线图而开发；计划可以取消、合并或推迟，代码越少但越有用越好。
- 不保留信息高度重复的多视图、多按钮或多入口。
- 没有可靠结构化数据时，不做自动统计、金额联动或健康结论。
- 页面中不展示虚构健康、工资或工作数据。
- 工作日数量以可编辑工作日历的最终状态为准。
- 法定节假日和调休以正式通知为准，按年份维护。
- 持久数据优先保存到 Cloudflare D1，不以浏览器缓存作为唯一数据源。
- Cloudflare Access 负责网页访问保护，健康上传接口使用独立密钥。
