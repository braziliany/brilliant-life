# 璀璨人生 v1.4 产品架构审查与路线图

> 本文是只读架构审查结果，不修改现有代码、配置、数据库或开发计划。路线图以“单人长期使用、真实数据可信、低运维负担”为前提。

## 执行摘要

璀璨人生已经越过“视觉原型”阶段，成为一个拥有真实数据链路的个人系统：Apple 健康数据从 iPhone 上传到 Cloudflare Worker，工作日历、工资、工作经历和健康数据保存在 D1，网页由 Access 保护，并可作为 PWA 使用。

当前架构适合继续作为 **Cloudflare 上的模块化单体**，没有必要拆成微服务，也没有必要更换数据库。未来三年，按现有“每日汇总”模型计算，数据规模极小；主要风险不是容量，而是：

1. `app/page.tsx` 已超过 1,000 行，多个领域状态和交互耦合；
2. `app/globals.css` 超过 52 KB，历史规则叠加导致移动端与桌面端相互覆盖；
3. 健康、日历、工资的领域规则仍混合在页面和 API 中；
4. 2026 年节假日硬编码，跨年后会产生业务错误；
5. 备份脚本已经存在，但恢复能力尚未通过定期演练证明；
6. Health Auto Export 与 iOS 后台调度不是可靠消息系统，网站必须容忍延迟、缺失和重复上传；
7. 当前测试重心偏输入校验，缺少数据库集成、迁移、关键用户流程和视觉回归保护。

因此，v1.4 不应以新增功能数量为目标。推荐将 v1.4 定义为：

> **架构收敛、数据可信、可恢复、可交接。**

v2.0 则应建立在至少 6～12 个月连续真实数据之上，定位为：

> **个人年度档案与长期趋势系统。**

---

## 1. 当前架构是否存在长期维护风险

### 1.1 总体判断

| 维度 | 当前判断 | 三年风险 | 建议 |
|---|---|---:|---|
| 部署架构 | Workers + D1 + Access 合理 | 低 | 保持模块化单体 |
| 数据容量 | 每日汇总模型非常轻量 | 低 | 不更换数据库 |
| 前端结构 | 单文件承担过多领域职责 | 高 | v1.4 优先拆分 |
| 样式系统 | 全局样式多次增量覆盖 | 高 | 建立作用域和设计令牌 |
| 领域规则 | 页面、API、常量之间存在分散 | 中高 | 提取领域层 |
| 数据迁移 | 有 Drizzle 迁移文件 | 中 | 增加迁移验证和回滚预案 |
| 测试 | 核心校验已有，流程覆盖不足 | 中高 | 增加集成与端到端测试 |
| 身份认证 | Cloudflare Access 合理 | 低 | 改用 Cloudflare IdP，不自建密码 |
| 数据恢复 | 有导出/恢复脚本，缺演练 | 高 | 建立可验证恢复流程 |
| 外部数据源 | iOS 后台同步有天然不确定性 | 中高 | 将延迟与缺失视为正常状态 |

### 1.2 最高风险：页面组件成为“上帝组件”

`app/page.tsx` 当前约 1,006 行、61 KB，同时负责：

- 首页与数据中心导航；
- 健康加载、趋势、同步诊断和 CSV 导出；
- 工作日历生成、节假日判断、编辑、备注和全年统计；
- 工资计算展示、历史保存和趋势；
- 工作经历表单、排序和详情；
- PWA 中的本地步数目标；
- 多种加载、错误和保存状态。

长期后果：

- 修改一个模块时容易触发其他模块重新渲染或样式变化；
- 状态依赖难以推理，跨午夜、跨月份和网络失败场景更容易遗漏；
- 无法针对单个领域进行隔离测试；
- 后续维护者需要先理解整页，才能安全修改一处。

这是 v1.4 最应优先解决的问题。

### 1.3 第二风险：全局 CSS 的级联债务

`app/globals.css` 当前约 390 行、52 KB。行数不算极端，但规则高度压缩，同一组件在文件不同位置和多个媒体查询中重复定义。此前移动端日历方框残留，就是早期选择器优先级高于后期样式造成的。

长期后果：

- 新样式需要不断提高选择器权重；
- 桌面修复可能破坏手机，反之亦然；
- 视觉回归依赖人工截图发现；
- 无法判断某条规则是否仍被使用。

### 1.4 第三风险：领域规则与界面耦合

以下规则属于领域逻辑，不应长期留在页面组件：

- 上海时区的“今天”和“当前月份”；
- 工作日与节假日判定；
- 个人排班覆盖后的工作日统计；
- 工资可保存月份与历史锁定规则；
- 健康数据的新鲜度、缺失指标和单位格式；
- 工作经历持续时间和排序。

如果这些规则在页面、API 和测试中各自实现一次，未来修改时会出现“前端显示一种结果、后端保存另一种结果”。工资策略已经提取到后端，这是正确方向，应推广到其他领域。

### 1.5 第四风险：静态年份规则

法定节假日和调休目前直接写入前端常量，且只覆盖 2026 年。进入 2027 年后：

- 周末仍能计算，但法定假日和调休会缺失；
- 工作日数量可能错误；
- 工资会被错误日历间接影响；
- 历史页面如果重新使用新的算法，也可能与当年已确认记录不一致。

节假日数据必须按年份版本化，并区分“官方基础日历”和“个人覆盖”。历史工资应继续使用已保存快照，而不是重新计算。

### 1.6 第五风险：测试与运行环境不完全一致

当前 API 校验测试有价值，但 `rendered-html.test.mjs` 在普通 Node 环境可能因 `cloudflare:` ESM 协议失败。测试环境与生产 Workers 环境不一致会降低测试可信度。

v1.4 应建立三层测试：

1. 纯函数单元测试：日期、工资、健康标准化；
2. Workers/D1 集成测试：API、迁移、鉴权、幂等写入；
3. 核心流程端到端测试：首页、健康刷新、日历编辑、工资保存、工作经历编辑。

## 2. 哪些模块应该拆分

### 2.1 拆分原则

推荐拆成 **领域模块**，不拆成独立服务。所有模块仍在同一个仓库、同一个 Worker 和同一个 D1 中运行。

不推荐：

- 为健康、工资、日历分别部署 Worker；
- 引入消息队列处理每天一次的健康汇总；
- 将前端拆成多个独立应用；
- 因“架构先进”而引入微服务、容器或 Kubernetes。

这些方案只会增加个人项目的运维负担。

### 2.2 推荐目录边界

```text
app/
├─ page.tsx                         # 仅负责页面入口与顶层组合
├─ components/
│  ├─ shell/                        # 顶部导航、页面壳、通用状态
│  ├─ home/                         # 首页 Hero 与摘要
│  └─ ui/                           # Button、Card、Status、EmptyState
├─ features/
│  ├─ health/
│  │  ├─ HealthDashboard.tsx
│  │  ├─ HealthSyncStatus.tsx
│  │  ├─ HealthTrend.tsx
│  │  ├─ health-client.ts           # 加载、刷新、导出
│  │  ├─ health-domain.ts           # 新鲜度、单位、缺失指标
│  │  └─ health.types.ts
│  ├─ calendar/
│  │  ├─ WorkCalendar.tsx
│  │  ├─ AnnualCalendar.tsx
│  │  ├─ CalendarNotes.tsx
│  │  ├─ calendar-domain.ts         # 工作日、覆盖和统计
│  │  └─ holiday-data/2026.ts
│  ├─ salary/
│  │  ├─ SalaryDashboard.tsx
│  │  ├─ SalaryHistory.tsx
│  │  ├─ salary-domain.ts
│  │  └─ salary.types.ts
│  └─ career/
│     ├─ WorkTimeline.tsx
│     ├─ WorkExperienceForm.tsx
│     └─ career-domain.ts
├─ lib/
│  ├─ shanghai-time.ts              # 唯一时区实现
│  ├─ api-client.ts                 # 统一错误与 JSON 处理
│  └─ csv.ts
└─ api/                             # 保持当前路由，内部调用领域服务
```

目录名称可以调整，但边界应保持。

### 2.3 必须优先拆分的模块

#### A. 健康模块

优先级最高。它同时处理外部数据源、格式兼容、单位换算、今日状态、趋势和缺失指标，失败场景最多。

拆分目标：

- 上传标准化与展示逻辑分离；
- “今日数据”和“历史最后一条”使用不同概念；
- 新鲜度和缺失指标成为可测试纯函数；
- 所有健康字段在一个类型定义中维护。

#### B. 工作日历模块

它是工资的上游数据源，属于关键业务模块。

拆分目标：

- 法定日历、个人覆盖、展示状态、工资工作日统计分层；
- 按年份加载日历数据；
- 历史月份只读，当前月份可编辑；
- 避免日期规则散落在 JSX 中。

#### C. 工资模块

工资算法本身已经后端化，但显示、保存、历史锁定和日历一致性仍应归为一个领域模块。

拆分目标：

- 计算政策、工资快照、保存资格明确区分；
- 历史记录始终读取快照；
- UI 不自行复制政策常量；
- 为未来年度汇总保留稳定接口。

#### D. 样式模块

不必一次性重写 CSS。推荐渐进式处理：

1. 先建立颜色、间距、字号、圆角、阴影令牌；
2. 新拆出的组件使用 CSS Modules 或明确的领域根类；
3. 旧样式只迁移正在修改的模块；
4. 配合桌面和 iPhone 视觉回归截图；
5. 最后删除确认无引用的全局规则。

### 2.4 暂时不应拆分的部分

- D1 不需要按领域拆成多个数据库；
- API 路由文件目前体量合理；
- Worker 安全响应头逻辑可以继续集中；
- 工作经历数据量与业务复杂度都很低；
- 首页本身不需要独立后端。

## 3. 哪些功能值得继续开发

功能应按“降低真实风险”和“真实使用频率”排序。

### 3.1 高价值：v1.4 必做

#### 1. 可验证的全量备份与恢复

价值：个人系统最重要的能力不是新增页面，而是数据可以带走、可以恢复。

最低完成标准：

- 定期导出 D1 SQL；
- 生成 SHA-256；
- 备份保存在 Cloudflare 之外的第二位置；
- 每季度在临时数据库执行恢复演练；
- 对比表数量、记录数量和关键样本；
- 形成恢复报告。

Cloudflare D1 Time Travel 可提供短期恢复，但保留窗口有限；长期个人档案仍需要独立导出。[Cloudflare D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)

#### 2. Cloudflare 账户身份登录

价值：减少 OTP 邮件延迟，避免自建密码系统。

推荐：

- Cloudflare Identity Provider；
- `Restrict to account members`；
- Cloudflare 账户开启 MFA；
- 应用和全局会话按个人风险偏好设置，最长不超过一个月；
- OTP 仅作备用。

官方支持使用 Cloudflare 账户成员身份作为 Access 策略条件。[Cloudflare Identity Provider](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/cloudflare/)

#### 3. 数据质量与同步连续性

现有同步状态中心是良好基础。值得继续增加的是：

- 最近 7 天哪些天未上传；
- 同一指标连续缺失多少天；
- 最近一次成功上传的指标清单；
- 只记录上传元数据，不记录原始敏感请求体；
- 明确区分“真实 0”和“未上传”。

这比增加更多健康指标更有价值。

#### 4. 节假日年度版本化

在 2027 年开始前必须完成：

- 每年一份官方基础日历；
- 数据带 `year` 和版本来源；
- 个人覆盖独立保存；
- 未配置年份明确提示“节假日尚未维护”，不静默按普通周末计算；
- 历史工资不因新日历版本改变。

#### 5. 核心流程测试

需要覆盖：

- 健康数据重复上传的幂等性；
- 当天无数据时不冒用昨天记录；
- 日历覆盖影响当前工资；
- 历史工资不可覆盖；
- 迁移从空库和旧库均可执行；
- Access 域名与 Workers 域名策略；
- iPhone 和桌面核心视觉不回归。

### 3.2 中价值：有真实数据后开发

#### 1. 年度收入与个税汇总

条件：至少有 3～6 个真实工资月份。只使用已保存工资快照，不对历史重新计算。

#### 2. 年度个人报告

条件：至少积累 6～12 个月连续数据。报告可以包含：

- 月均步数、活动能量、睡眠和静息心率；
- 工作日和休息日分布；
- 已保存工资与个税总额；
- 工作经历变更。

报告只做事实汇总，不输出医学结论或心理推断。

#### 3. 数据导出中心

提供面向用户的 JSON/CSV/SQL 导出清单和生成时间，但恢复操作仍应保持高门槛，不在普通页面放“一键覆盖数据库”。

### 3.3 低价值：仅在出现明确需求时开发

- 年度工作日 CSV；
- 更多健康指标；
- 更复杂的工资加项；
- 通知和提醒；
- 首页摘要调整。

## 4. 哪些功能应该永久放弃

“永久放弃”意味着除非产品定位发生根本变化，否则不再进入路线图。

### 4.1 应用内自建账号密码系统

原因：

- 网站仅一人使用；
- Cloudflare Access 已解决身份验证；
- 自建系统需要密码哈希、会话、找回、限流、CSRF、防撞库和审计；
- 会形成第二道登录和第二套安全边界；
- 收益低于长期维护成本。

### 4.2 多用户、社交、排行榜与共享社区

原因：这会改变数据模型、隐私责任、授权体系和产品定位，不再是个人系统。

### 4.3 高度可配置的首页／低代码搭建器

原因：唯一用户同时也是项目所有者，直接维护固定页面比构建配置系统更简单可靠。

### 4.4 重复视图和重复入口

永久放弃：

- 工作经历“列表 + 时间线”双视图；
- 同一健康数据的多个近似图表；
- 为每个模块重复建立独立首页；
- 仅换排列方式、不增加信息价值的视图切换。

### 4.5 从自由文本自动推导工资或统计

例如从请假备注、加班备注中自动计算扣款或加班费。自由文本不是可靠结构化数据，错误金额的风险高于便利。

### 4.6 医疗诊断、健康评分和 AI 健康建议

原因：当前数据不完整，且个人项目不应承担医疗结论风险。可以展示趋势和缺失，但不应判断疾病、健康等级或给出治疗建议。

### 4.7 保存高频原始 HealthKit 明细

当前产品目标只需要每日汇总。保存分钟级心率、逐条步数和完整原始健康 JSON 会显著增加数据量、敏感性和泄露影响，却不产生相称价值。

### 4.8 为个人项目引入微服务架构

包括多个 Worker、事件总线、服务发现和容器平台。当前规模下属于纯粹的架构负担。

## 5. 未来三年的数据增长风险

### 5.1 按当前模型估算

假设 2026-08 至 2029-08 连续使用：

| 数据 | 写入模型 | 三年数量级 | 容量风险 |
|---|---|---:|---:|
| 健康汇总 | 每日最多 1 行 | 约 1,096 行 | 极低 |
| 日历覆盖 | 每日最多 1 行 | 最坏约 1,096 行 | 极低 |
| 日历备注 | 每月 1 行 | 约 36 行 | 极低 |
| 工资历史 | 每月 1 行 | 约 36 行 | 极低 |
| 工作经历 | 事件驱动 | 通常少于几十行 | 极低 |

即使考虑索引、迁移和 SQLite 页开销，三年数据仍远低于需要更换数据库的程度。

### 5.2 真正的数据风险

#### A. 数据语义漂移

比容量更危险：

- Health Auto Export 字段名或 JSON 版本改变；
- 能量单位从 kcal 变为 kJ；
- 手表改名导致来源变化；
- 节假日每年不同；
- 工资政策将来改变；
- `0`、`null` 和“未上传”含义混淆。

应对：所有外部数据先标准化，记录来源、更新时间和解析版本；政策变化必须生成新版本，不覆盖历史语义。

#### B. “每日覆盖”丢失信息

`health_daily` 以日期唯一并覆盖更新，适合当前汇总模型，但无法回答“这一天上传过几次、某字段何时从空变为有值”。

不建议保存原始健康数据；可以新增低敏感度的 `ingestion_runs` 元数据表，只保存：

- 上传时间；
- 覆盖日期范围；
- 接收的指标名；
- 成功/失败；
- 解析版本；
- 不保存原始请求体和 API Key。

#### C. 迁移累积

当前已有多份 Drizzle 迁移。三年后风险是：

- 新环境不能从零完整迁移；
- 某次迁移只在生产手工执行，没有进入仓库；
- schema 与实际 D1 不一致。

应对：每个版本在空库和上一版备份上验证迁移，并保留迁移清单。

#### D. 备份存在但无法恢复

只有 SQL 文件不等于可恢复。风险包括文件损坏、备份未更新、命令版本变化、恢复目标选错和密钥丢失。

应对：离线副本、校验和、恢复演练、恢复报告和账号恢复码分开保存。

#### E. 如果误转向原始明细，数据量会急剧上升

例如每分钟心率会达到每年几十万行，多个指标三年可能达到百万级记录。此时容量仍未必是首要问题，但查询、迁移、导出和隐私风险会明显上升。因此应继续坚持每日汇总。

## 6. 如何保证个人数据安全

### 6.1 安全目标

按优先级排列：

1. 未授权者不能访问网站或 API；
2. 健康上传密钥泄露后可以快速吊销；
3. 数据误删或错误迁移后可以恢复；
4. GitHub、日志、备份中不出现密钥和原始敏感载荷；
5. 即使某个设备丢失，攻击者也不能长期访问；
6. 收集的数据只限于产品真正使用的字段。

### 6.2 身份与访问控制

- 使用 Cloudflare Access，不自建账号密码；
- 启用 Cloudflare Identity Provider，并限制为当前账户成员；
- Cloudflare 账户启用 MFA，保存恢复码；
- 会话期限在便利与设备丢失风险之间权衡，建议 7～30 天；Cloudflare Access 支持应用、策略和全局多层会话期限。[Access 会话管理](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)
- OTP 作为备用，不作为唯一方式；
- 定期检查 Access 审计日志和账户成员；
- 不将 Access 绕过逻辑扩展到除 localhost 以外的主机。

### 6.3 健康上传接口

- `HEALTH_INGEST_API_KEY` 只保存在 Cloudflare Secret 和 iPhone；
- 每 3～6 个月轮换，设备丢失或截图泄露时立即轮换；
- 对上传接口增加速率限制和请求体大小上限；
- 继续严格校验日期、单位、字段范围和内容类型；
- API 返回只包含必要摘要；
- 日志不得记录完整请求头、密钥或原始健康 JSON；
- 未来如果引入 ingestion 元数据，只记录指标名和状态。

### 6.4 数据库与备份

- 每周或每月自动导出 D1；
- 至少保留一份 Cloudflare 之外的加密副本；
- 备份文件使用强加密，密钥不与备份放在同一位置；
- 每季度在临时数据库执行恢复演练；
- 迁移和批量更新前创建备份并记录 Time Travel bookmark；
- Cloudflare D1 Time Travel 适合短期误操作恢复，但不能替代长期独立备份。[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)
- 恢复操作不得放在普通网页按钮中，继续保留显式确认和安全备份步骤。

### 6.5 应用安全

- 保持安全响应头和 `frame-ancestors 'none'`；
- 逐步减少 CSP 中的 `'unsafe-inline'`，但不要在没有构建兼容验证时强行移除；
- 所有写入 API 继续执行服务端授权，不能依赖前端隐藏按钮；
- 删除操作必须确认，历史工资继续不可修改；
- 依赖升级先构建和测试，不盲目追最新主版本；
- 每季度执行依赖审计；
- GitHub 开启 2FA，限制令牌权限，避免长期使用宽权限 Personal Access Token。

### 6.6 数据最小化

- 只保存每日汇总，不保存逐分钟健康原始数据；
- 不保存健康 App 中未被网站使用的指标；
- 不保存邮箱验证码、Access JWT 或 API Key；
- CSV 导出后由用户自行保护，本地导出文件不进入 Git；
- 敏感备份目录必须加入 `.gitignore`。

## 7. v1.4 产品路线图

### v1.4 产品定位

**版本主题：可信、可维护、可恢复。**

不以新增大模块为成功标准。完成标准是：任何维护者都能理解模块边界、验证数据、恢复数据库，并在不破坏其他模块的情况下修改单一功能。

### v1.4.0：架构收敛

#### 目标

- 将 `app/page.tsx` 拆为领域组件；
- 建立唯一的上海时区工具；
- 提取健康、日历、工资、职业领域纯函数；
- 建立 API 客户端与统一错误模型；
- 新拆组件使用有作用域的样式。

#### 验收标准

- 顶层页面只负责组合和少量导航状态；
- 健康、日历、工资模块可以独立测试；
- 拆分前后核心界面截图一致；
- 不改变数据库和业务结果；
- 不新增用户可见功能。

### v1.4.1：数据可信

#### 目标

- 健康上传连续性与指标缺失记录；
- 区分真实零值、空值和未上传；
- 节假日按年份版本化；
- 工资历史继续使用快照；
- 建立数据字典和字段语义说明。

#### 验收标准

- 网站能明确解释“今天为什么没有体重”；
- 未维护年份不会给出假精确工作日；
- 外部字段变化会明确失败或记录，不静默丢弃；
- 历史工资不会因政策或日历更新改变。

### v1.4.2：安全与可恢复

#### 目标

- Cloudflare 账户登录 + MFA；
- OTP 备用；
- 上传接口速率限制与大小限制；
- 自动备份和季度恢复演练；
- 密钥轮换清单；
- README、部署和恢复文档更新。

#### 验收标准

- 新设备可按文档完成部署；
- 临时 D1 可以从备份恢复；
- Git 仓库扫描不到密钥；
- 丢失 iPhone 后有明确的吊销步骤；
- Access、GitHub 和 Cloudflare 账户均启用强认证。

### v1.4.3：质量门槛

#### 目标

- Workers/D1 集成测试；
- 关键流程端到端测试；
- 桌面与 iPhone 视觉回归；
- 数据迁移测试；
- 发布前自动检查清单。

#### 验收标准

- `npm test` 在全新环境稳定通过；
- 每次发布自动验证健康读取、日历编辑、工资保存权限和工作经历读取；
- 移动端和桌面端关键组件有基准截图；
- 失败发布可以回退到上一 Worker 版本。

### v1.4 明确不包含

- 自建账号密码；
- 年度大屏；
- AI 健康建议；
- 多用户；
- 主题系统；
- 新数据库；
- 微服务拆分；
- 大规模视觉重做。

## 8. v2.0 产品路线图

### v2.0 启动条件

必须同时满足：

1. v1.4 的模块拆分、恢复演练和测试门槛已完成；
2. 至少有 6～12 个月连续真实数据；
3. 工资历史至少有 6 个已确认月份；
4. 健康同步缺失率已知并可解释；
5. 下一年度节假日数据已版本化维护。

如果条件不满足，不应提前开发年度报告。

### v2.0 产品定位

**个人年度档案与长期趋势系统。**

核心不是增加更多日常录入，而是把已经积累的数据组织成可回顾、可导出、可迁移的长期个人档案。

### v2.0.0：年度档案

- 年度健康事实摘要；
- 年度工作日、休息日和个人调整统计；
- 年度已保存工资、扣除和个税汇总；
- 年度职业经历变化；
- 每项统计都可以追溯到原始月/日记录；
- 缺失月份明确标记，不做推算填充。

### v2.0.1：数据迁移与所有权

- 全量 JSON/CSV/SQL 导出；
- 导出清单包含 schema 版本、生成时间、校验和；
- 提供只读导入预检报告；
- 正式恢复仍通过受控命令执行；
- 支持迁移到新的 Cloudflare 账户或独立 SQLite 环境。

### v2.0.2：长期趋势

- 年对年健康趋势；
- 工资与工作日的年度变化；
- 职业时间线与年度节点；
- 只展示事实和趋势，不生成医疗、财务或人生价值判断。

### v2.0.3：可选的个人回顾

只有用户持续使用后再评估：

- 年度文字回顾；
- 手工选择重要事件；
- 导出为可打印报告；
- 不自动分析私人文本，不默认上传到第三方 AI。

### v2.0 仍然不做

- 多用户 SaaS；
- 社交分享；
- 医疗诊断；
- 自动理财或税务申报；
- 原始高频健康数据仓库；
- 复杂工作流平台；
- 无明确用途的可视化堆叠。

## 10. 架构决策结论

| 决策 | 结论 |
|---|---|
| 是否更换 D1 | 否，三年容量远未构成压力 |
| 是否引入微服务 | 否，保持模块化单体 |
| 是否自建登录 | 永久放弃，使用 Cloudflare Access |
| v1.4 是否增加大功能 | 否，以架构、数据和恢复为主 |
| 是否保存原始 HealthKit 明细 | 否，继续每日汇总 |
| 是否开发年度报告 | 有 6～12 个月真实数据后进入 v2.0 |
| 是否重写全站 CSS | 否，随模块拆分渐进迁移 |
| 是否允许历史工资修改 | 否，保持快照不可变 |
| 是否继续扩展健康指标 | 仅在出现明确查看需求时 |
| 最重要的下一步 | 模块拆分、年度日历、恢复演练、测试 |

## 最终建议

璀璨人生不需要变成“功能更多的网站”，而应该变成“十年后仍然能打开、能理解、能恢复的个人档案”。

v1.4 的成功不是新增多少卡片，而是做到：

- 每条数据的来源与含义清楚；
- 每个领域可以独立维护；
- 每次修改有测试保护；
- 每次误操作可以恢复；
- 每项新增功能都能证明真实价值；
- 用户始终拥有完整的数据导出权。

在这个标准下，当前技术底座是合适的，真正需要改变的是代码边界、数据治理和运维纪律，而不是平台。
