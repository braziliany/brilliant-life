## Step 2：最小健康上传元数据

状态：已完成。

拟新增 `health_ingestion_runs`，只保存接收时间、覆盖日期、指标键、导入天数、解析状态和限长来源类别。禁止保存原始 JSON、API Key、Access Token、完整请求头、设备名称和 HealthKit 明细。

该表用于回答最近一次上传时间、最近 7 天上传连续性、某次上传包含的指标以及“完全未上传”和“收到但未导入”的区别。需要新增 migration，并在临时 D1 验证后才可应用生产。

实施结果：

- 新增 migration `0012_sharp_lake.sql`，包含上传日志表和接收时间索引；
- 迁移前完成生产 D1 备份；
- 生产备份先恢复到独立临时 D1，旧数据一致性验证通过后再应用迁移；
- 临时库升级后保留全部既有数据，新表初始为空；生产迁移成功后临时库已删除；
- GET 健康接口保持原字段并新增 `ingestions`，旧客户端继续兼容；
- 现有同步中心新增最近 7 天成功、异常、未收到日期和今天最近一次指标覆盖说明；
- 原始 JSON、API Key、Access Token、请求头、设备名称和 HealthKit 明细均未保存。

## Step 3：节假日年度版本化

状态：已完成。

将 2026 官方数据原样迁移到 `app/features/calendar/holiday-data/2026.ts`，增加 `getHolidayCalendar(year)`。未配置年份返回 `unconfigured`，不得静默作为完整官方日历驱动工资。2026 节假日、248 个全年工作日和工资链必须完全不变。无 schema 变化。

实施结果：

- 2026 节假日区间和调休工作日已原样迁入独立年度文件；
- `getHolidayCalendar(year)` 对 2026 返回 `configured`，其他年份明确返回 `unconfigured`；
- 未配置年份仍可浏览星期布局和维护个人排班，但界面明确提示官方数据缺失，并禁止保存或同步工资；
- 2026 全年工作日、2026-07 工作日及冻结工资回归结果均保持一致；具体个人金额只保留在私有记录中；
- 无 API、数据库和 migration 变化；完整构建与 43 项自动化测试通过。

## Step 5：发布门禁与 README

状态：已完成。

增加统一 `npm run verify`，覆盖构建、API、Health、Calendar、Salary、Career、迁移和修复后的 rendered HTML 测试。README 必须说明真实 D1、Access、健康上传 Secret、migration、备份恢复和部署流程。纯测试或文档修改不部署 Worker。

Step 1 发布审计发现：Sites 完整归档超过 10 MiB 限制，而 Wrangler 的实际 Worker 模块远低于该限制。Step 5 应检查归档中不必要的构建文件并明确正式发布路径；不得为了压缩归档改动业务代码或升级依赖。

实施结果：

- 新增统一 `npm run verify`，依次执行生产构建、43 项领域/API 回归、2 项本地 D1 migration 测试和 1 项 Workers HTML 测试；
- 修复 `rendered-html` 测试，改由临时 Wrangler Workers 运行时读取真实构建产物，并核对首屏内容与安全响应头；
- 临时 Worker、本地数据库、配置和日志均隔离创建并自动清理；
- README 已按真实项目重写，覆盖 D1、Access、健康上传 Secret、migration、备份恢复、年度日历和发布流程；
- 当前正式发布路径明确为 `npx wrangler deploy`；Sites 完整归档约束不再作为正式发布路径；
- 构建目录约 38 MiB，主要来自霞鹜文楷字体在 client/server 构建中的重复副本；实际 Wrangler Worker 上传远低于该限制。保留现有字体和 UI，不做破坏性压缩或依赖升级；
- 本步骤仅修改测试、脚本和文档，不发布 Worker。
