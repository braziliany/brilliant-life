# 璀璨人生 v1.4 Sprint 6：D1 备份恢复与数据可靠性基线实施计划

## 1. 目标

建立可验证的 D1 备份、非生产恢复演练、数据字典和灾难恢复手册，使个人数据能够在多年后被理解、校验和恢复。

> 只增强数据可靠性，不改变线上业务行为，不以“生成了 SQL 文件”代替恢复验证。

## 完成摘要（2026-08-08）

- 生产 D1 已完成只读 schema、索引、行数和关键快照审计；
- 备份脚本已生成 `database.sql`、`metadata.json` 和 SHA256；
- 恢复脚本默认阻止生产恢复，并在导入前验证哈希、目标身份和安全备份；
- 新增自动验证脚本，核对表、索引、行数、工资快照、最新健康记录和职业顺序；
- 备份已成功恢复到独立 APAC 测试 D1，自动一致性验证通过；
- 临时恢复库在核对 database_id 后删除，生产库未执行恢复或写入；
- 数据字典、备份说明、部署恢复手册和演练记录已完成；
- UI、API、schema、migration 和全部领域逻辑保持不变。

## 3. 生产 D1 只读审计（2026-08-08）

### 数据库身份

| 项目 | 实际值 |
|---|---|
| 数据库名称 | `pulse-health-dashboard-db` |
| database_id | 已记录于私有运维文档，公开版本脱敏 |
| 创建时间 | 已核对，公开版本脱敏 |
| D1 文件大小 | 已核对，公开版本脱敏 |
| Worker 基线版本 | 已记录于私有运维文档 |

Wrangler `d1 list` 返回的 `num_tables` 为 0，但直接读取 `sqlite_schema` 已确认业务表存在，因此不能把列表接口的该字段作为恢复验收依据。

### 实际表与行数

| 表 | 行数 | 主要用途 |
|---|---:|---|
| `health_daily` | 已核对 | Apple 健康每日汇总 |
| `calendar_overrides` | 已核对 | 个人工作日覆盖 |
| `calendar_notes` | 已核对 | 月度排班备注 |
| `salary_records` | 已核对 | 已保存工资快照 |
| `salary_settings` | 已核对 | 工资参数 |
| `work_experiences` | 已核对 | 工作经历 |

另有 Cloudflare 内部表 `_cf_KV`，备份应完整保留，但业务一致性统计不把它计入六张业务表。

### 关键恢复基线

- `salary_records` 的目标月份历史快照已逐字段核对，公开版本不记录个人金额；
- 最新健康记录的日期和来源已核对，公开版本不记录真实日期；
- 工作经历排序已核对，公开版本不记录真实任职时间；
- D1 远程环境拒绝 `PRAGMA integrity_check`（`SQLITE_AUTH`），因此恢复验收使用 schema、行数、唯一索引和关键快照的只读查询，不伪造“完整性检查通过”。

算法回归样例与生产历史快照属于不同用途。Sprint 6 只验证真实历史数据，不修改历史记录。

## 4. 现有能力审计

项目已经具备：

- `npm run db:backup`
- `scripts/backup-d1.ps1`
- `npm run db:restore`
- `scripts/restore-d1.ps1`
- `docs/D1备份与恢复.md`
- `backups/` Git 忽略规则

现有不足：

1. 备份只有 SQL 和控制台 SHA256，没有 `metadata.json`；
2. 没有保存表清单、行数、数据库 ID、Worker 版本和关键快照；
3. 恢复脚本默认数据库是生产库，误操作风险偏高；
4. 恢复完成后只提示人工检查，没有自动一致性比较；
5. 没有真正恢复到测试 D1 的演练记录；
6. 数据字典和新环境灾难恢复手册不完整。

## 5. 修订后的实施步骤

### Step 1：确认生产备份可导出

- 使用现有只读导出流程生成一次生产 SQL 备份；
- 验证文件非空并计算 SHA256；
- 不提交 SQL 备份，不输出个人数据到 GitHub 或日志文档。

### Step 2：增强备份与恢复脚本

- 备份目录按时间隔离；
- 生成 `database.sql` 和 `metadata.json`；
- metadata 保存数据库身份、备份时间、文件大小、SHA256、表行数和关键快照；
- 恢复目标必须显式指定；
- 默认拒绝恢复到生产库，生产恢复需要额外明确开关；
- 新增只读验证能力，对恢复库与 metadata 做一致性比较。

### Step 3：非生产 D1 恢复演练

- 创建专用临时恢复数据库；
- 导入本次 SQL；
- 验证六张业务表、唯一索引、各表行数、工资快照、最新健康日期和职业排序；
- 记录演练结果；
- 删除临时恢复数据库前再次确认其 ID 与生产 ID 不同。

### Step 4：数据字典

新增 `docs/数据字典.md`，以生产 `sqlite_schema` 与 `db/schema.ts` 交叉核对字段、类型、空值语义、唯一约束和数据来源。

### Step 5：部署与恢复手册

新增 `docs/部署与恢复手册.md`，覆盖新环境部署、绑定 D1、迁移、恢复、Access 验证、健康上传密钥轮换和回滚。

### Step 6：最终回归

执行：

```powershell
npm run build
node --test tests/api-validation.test.mjs
node --test tests/health-domain.test.mjs
node --test tests/calendar-domain.test.mjs
node --test tests/salary-domain.test.mjs
node --test tests/career-domain.test.mjs
git diff --check
```

并确认冻结范围零差异。若只有脚本和文档变化，不生成新的 Worker 发布版本。

## 7. 风险控制

| 风险 | 控制 |
|---|---|
| 把恢复演练导入生产库 | 目标数据库必须显式指定，生产恢复需要双重开关，并比对 database_id |
| 备份文件泄露个人数据 | `backups/` 保持 Git 忽略，文档只记录哈希和统计 |
| 只有备份没有可恢复性 | 必须完成独立测试 D1 恢复和自动比对 |
| 用算法样例替代历史数据 | 以生产历史快照逐字段比对，公开文档不记录个人金额 |
| Wrangler 表数元数据误导 | 直接查询 `sqlite_schema` |
| D1 禁止 PRAGMA 完整性检查 | 使用 schema、索引、行数和关键记录组合验证 |

## 8. 决策门

本文件和生产只读审计完成后，才允许修改备份脚本。任何恢复命令必须指向新建的非生产数据库；若无法证明目标 ID 与生产 ID 不同，立即停止恢复。
