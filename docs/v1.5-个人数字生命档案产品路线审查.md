# 璀璨人生 v1.5：个人数字生命档案产品路线审查

> 审查基线：`main@de05d7b`
> 当前阶段：v1.4 Stable Foundation
> 审查日期：2026-08-09

## 1. 产品定位结论

推荐定位：**C——个人数字生命档案**。

璀璨人生应从“个人信息管理工具”升级为：

> 以时间为主轴、以事实为基础、能够长期回顾人生变化的个人数字生命档案。

原因：

- 当前数据已经覆盖健康、工作时间、收入和职业经历，不再是单一工具；
- 四个领域天然具有时间属性，适合形成年度档案和长期趋势；
- 现有数据来自真实来源，已经具备可信度、备份、恢复和测试基础；
- 单人使用使产品可以保持克制，不必为通用市场牺牲个人价值；
- 长期价值不在于增加更多录入功能，而在于多年后仍能理解过去的生活状态。

不选择其他定位：

| 方向 | 不推荐原因 |
|---|---|
| 单纯健康 App | 缺少医疗级数据与诊断能力，也会浪费已有工作、工资和职业数据 |
| 生产力或 Todo 工具 | 当前没有任务、协作、提醒体系，引入后会偏离长期档案定位 |
| 财务管理工具 | 当前只记录工资事实，不具备资产、负债、预算、消费和投资模型 |
| 人生建议系统 | 数据连续性尚不足，不应从不完整事实推导人生建议 |

产品边界应是：保存事实、展示变化、说明数据完整度，但不评价人生好坏。

## 2. 用户价值

v1.5 应回答：

1. 这一年发生了什么？
2. 我的健康、工作和收入发生了哪些变化？
3. 这些结论来自哪些数据，数据是否完整？
4. 多年以后，我还能否导出、理解并恢复这些记录？

核心价值不是“统计更多”，而是事实可追溯、缺失可解释、历史不漂移、年份可比较、数据归用户所有。

## 3. 核心价值模型

### 3.1 Person

逻辑上需要，数据库中暂时不需要。当前只有一个用户，立即创建 `Person` 表只会引入无实际用途的外键和身份体系。建议将 Person 作为隐含上下文：

```text
LifeArchive
└── owner: current-person
```

只有出现多人档案、家庭档案、数据继承或明确档案移交时，才重新评估持久化 `Person`；v1.5 不得借此发展多用户系统。

### 3.2 时间层级

```text
Year
├── Month
│   ├── Day
│   └── Monthly facts
└── Annual facts
```

- Day：健康汇总、工作状态、个人排班；
- Month：工资快照、月度工作日、职业阶段；
- Year：年度事实汇总、覆盖率、趋势和重要事件。

年度数据必须由已有日/月事实聚合，不能绕过来源生成孤立数字。

### 3.3 Life Domains

| 领域 | 当前数据 | 未来候选 | v1.5 结论 |
|---|---|---|---|
| Health | 步数、能量、运动、睡眠、体重、心率 | 年度趋势、连续性 | 必须加入 |
| Career | 公司、职位、任职时间、工作内容 | 阶段变化、年度职业节点 | 必须加入 |
| Finance | 工资、扣除、个税、实发 | 年度收入与月份覆盖率 | 必须加入 |
| Time | 工作日、休息日、节假日、个人调整 | 工作/休息结构 | 必须加入 |
| Events | 尚无结构化数据 | 旅行、搬迁、项目、决定 | 延后至独立 Sprint |
| Growth | 尚无可靠结构化来源 | 学习、技能、阅读 | 暂不加入 |

## 4. 年度人生档案

年度档案建议命名为“璀璨人生 2026”。每个数字必须同时具备数值或事实、数据来源、覆盖范围、缺失说明和计算版本。

### 4.1 健康回顾

可直接生成：有记录天数和覆盖率、有效日期日均步数、运动天数和时长、能量趋势、有效睡眠均值、体重变化、静息心率趋势、上传成功与缺失日期。

禁止用 0 填补未上传日期、把缺失解释为没有运动，或给出健康评分、疾病风险和医疗建议。

### 4.2 工作回顾

可生成官方工作日、个人实际工作日、休息日、节假日、个人调班数量、年内任职公司和职位，以及入职、离职或职位变化。跨年职业经历必须按与本年度的时间交集统计。

### 4.3 财务回顾

只汇总已保存工资月份，包括月份覆盖率、应发与实发合计、个税合计和月度变化。缺失月份不得按平均值补齐，当前工资政策不得重算历史快照。

“工作投入产出”容易被误解为人生效率评价，不建议作为核心指标。

### 4.4 时间回顾

可生成工作日、周末、法定假日、调休上班、个人工作/休息修改和月度分布。未配置官方节假日的年份不得生成正式年度时间或工资总结。

### 4.5 LifeEvent

建议加入事实型事件，不发展为复杂日记系统：

```text
LifeEvent {
  id
  date
  endDate?
  domain
  type
  title
  note?
  source
  createdAt
  updatedAt
}
```

自动事件可包括入职、离职、职位变化和明确的数据里程碑；主动事件可包括旅行、搬迁、项目完成、学习经历和重要决定。自动事件必须标记来源并允许隐藏，不能把算法推测写成真实事件。

## 5. 年度数据模型

推荐混合模型：

```text
年度进行中 → 实时计算 AnnualSummaryDraft
用户确认或年度结束 → 冻结 AnnualSnapshot
```

```text
AnnualSummaryDraft {
  year
  generatedAt
  calculationVersion
  status: draft
  completeness
  health
  career
  finance
  time
  events
  sources
  warnings
}

AnnualSnapshot {
  year
  frozenAt
  schemaVersion
  calculationVersion
  sourceCutoff
  payload
  checksum
  status: frozen
}
```

每个领域摘要统一包含 `facts`、`coverage`、`sources` 和 `warnings`。覆盖率不是附属信息，而是年度档案的核心字段。

快照规则：年度进行中只生成草稿；冻结前显示缺失项；冻结必须由用户确认；冻结后不随算法变化自动修改；修复只能生成带原因的新修订；删除源数据前必须提示受影响快照。v1.5 初期只设计和测试逻辑模型，不立即创建快照表。

## 6. Sprint 路线

### Sprint 8：年度档案计算基础

- 建立 `annual/domain.ts` 和 `AnnualSummaryDraft`；
- 完成年度范围、月份覆盖、数据完整度及四领域事实聚合；
- 不修改数据库、不新增年度页面、不创建快照、不实现 LifeEvent；
- 验收缺失不填零、历史快照不重算、跨领域结果一致。

### Sprint 9：可信度与解释层

- 统一 `coverage`、`sources`、`warnings`；
- 区分无记录、真实零值和年份未配置；
- 定义允许同比的指标和可比条件；
- 不做自动建议、健康评分或主观结论。

趋势之前必须先证明数据具有可比性。

### Sprint 10：年度报告页面

- 增加只读“我的 2026”；
- 展示健康、工作、财务和时间事实；
- 每个模块显示覆盖率与缺失说明；
- 支持年份切换和可信空状态；
- 初期只展示实时草稿，不冻结快照。

### Sprint 11：人生事件系统

- 先完成 LifeEvent 数据模型和隐私审查；
- 实现最小主动记录和明确的职业自动事件；
- 不从自由文本或健康数据推断事件；
- 这是首个可能需要 schema/migration 的 Sprint，必须单独审批。

### Sprint 12：年度冻结与档案导出

- 评估并实现 `AnnualSnapshot`；
- 用户确认后冻结；
- 提供带版本、来源、覆盖率、生成时间和校验和的 JSON 导出；
- 建立快照不可变测试；
- 仅在年度报告经过真实使用验证后进入。

顺序：年度聚合 → 可信解释 → 年度报告草稿 → 人生事件 → 快照与导出。复杂年度同比应等待两个完整年份。

## 7. 技术路线

继续保持 React/vinext、Cloudflare Workers、Cloudflare D1、Cloudflare Access 和模块化单体。v1.5 不需要新数据库、数据仓库、队列、分析服务、微服务、对象存储或第三方 AI 服务。

三年数据量仍很小，年度聚合属于轻量查询。只有出现可重复性能问题并由测试证明 D1 无法满足时，才重新评估基础设施。

## 8. 隐私与数据边界

数据原则：

1. 只收集产品实际使用的数据；
2. 不保存无必要的 HealthKit 原始明细；
3. 所有年度结论标记来源；
4. 用户可以查看、导出和删除数据；
5. 缺失数据不推测、不补齐；
6. 不用健康、财务和职业数据进行人格或能力判断；
7. 明确区分自动内容与用户记录；
8. 公开仓库、日志和测试只使用脱敏或合成数据。

数据导出优先级高于复杂趋势，建议支持单年度 JSON、单领域 CSV、全量档案清单、schema/计算版本、生成时间、校验和与覆盖说明。

数据删除必须先展示影响范围、提供导出、创建备份并二次确认。实施顺序建议为单条事件、领域日期范围、年度、全部档案。

数据审计建议记录来源、创建/更新时间、解析/计算版本、快照生成时间和修订原因；禁止记录原始认证头、密钥、Token、完整健康 JSON和包含敏感值的冗长日志。

## 9. v1.5 禁止项

- AI：健康诊断、心理分析、人格推断、自动人生建议、默认发送私人档案；
- 社交：分享、排名、比较、社区和公开年度报告；
- 产品化：多用户、商业账户、SaaS、支付和自建账号密码；
- 技术扩张：新数据库、数据仓库、队列、微服务、Kubernetes 和高频健康原始数据仓库。

## 10. 测试体系

年度聚合测试覆盖空年份、部分月份、完整年份、零值与缺失值、跨年职业经历、健康指标覆盖率和未配置日历年份。

跨领域测试必须验证 `Calendar → Salary snapshot → AnnualSummary`：年度工作日来源正确，财务只采用已保存工资，当前政策不重算历史，缺失月份不推算。

历史冻结测试使用纯合成的 2026 年度档案 fixture，验证冻结快照不随算法升级变化，新版本只能生成修订，checksum 能识别变化，源数据变化不会静默改写快照。

继续以 `npm run verify` 为门禁，逐步加入 annual domain、跨领域、rendered HTML、snapshot migration 和 export schema 测试。

## 11. 风险分析

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 数据缺失导致错误结论 | 高 | 覆盖率、警告、禁止推算 |
| 数据解释错误 | 高 | 事实定义、来源、计算版本、回归测试 |
| 健康与财务隐私扩大 | 高 | 最小化、Access、脱敏、受控导出 |
| 年度快照设计错误 | 高 | 先草稿后冻结、版本化、独立审批 |
| 数据模型过度设计 | 中高 | Sprint 8 先做纯函数，不立即建表 |
| 新功能增加维护复杂度 | 中 | 模块化单体、每 Sprint 单一目标 |
| AI 过早加入 | 中 | 明确禁止进入 v1.5 |
| 基础设施过度扩张 | 中低 | 新基础设施必须有实测证据 |
| D1 容量不足 | 低 | 当前每日汇总模型三年规模很小 |

## 12. Definition of Done

v1.5 完成必须同时满足：

- Health、Career、Finance、Time 能生成年度事实摘要；
- 所有指标包含来源和覆盖说明；
- 缺失数据不以 0 代替，也不进行推算；
- 历史工资只读取已保存快照；
- 未配置日历年份不能生成正式时间或工资结论；
- 年度报告支持只读年份切换和可信空状态；
- LifeEvent 区分用户记录与自动事实；
- 年度快照确认后不可静默改变；
- 提供至少一种结构化年度导出；
- 导出和测试不包含密钥或未脱敏个人数据；
- 新 migration 通过空库和中间 schema 测试；
- `npm run verify` 全部通过；
- 备份、恢复和回滚说明同步更新；
- 不引入新数据库、AI、社交、多用户或微服务。

## 最终结论

> 璀璨人生 v1.5 是否应该转型为个人数字生命档案系统？

**结论：是。**

璀璨人生已经拥有健康、时间、收入和职业四条真实数据链路，也完成了领域拆分、备份恢复、历史冻结和发布门禁。继续把它定义成单一健康或工资工具，会低估现有数据之间的长期关联。

转型必须保持克制：从年度事实开始，先解释完整度再做趋势，先实时草稿再做年度冻结，不引入 AI 判断，不扩张为多用户产品，不更换当前技术底座。

```text
v1.5  年度事实与个人档案
↓
v1.6  可信年度冻结、导出与删除
↓
v2.0  跨年度比较与长期人生轨迹
```
