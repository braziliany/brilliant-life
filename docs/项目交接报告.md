## 1. 项目目标

“璀璨人生”是一个仅供本人使用的个人生活管理网站，目标是在一个受保护的界面中统一查看和维护：

1. Apple 健康与 Apple Watch 数据；
2. 工作日、法定节假日、调休和个人排班；
3. 按真实工作日计算的当月工资和历史工资；
4. 可长期维护的工作经历；
5. 后续可扩展的个人数据备份、年度统计与长期趋势。

项目坚持“保护性开发”：只开发已经出现的真实需求，优先局部增量修改，不为了功能数量破坏现有视觉、交互或数据可靠性。

## 4. 已实现功能

### 首页与 PWA

- 网站名称与品牌统一为“璀璨人生”；
- 每日轮换《原神》短句；
- 首页展示今日步数、本月工作日、预计工资和工作经历数量；
- 首页与数据中心双页导航；
- iPhone PWA 安装、自定义图标、独立窗口运行；
- Service Worker 对个人数据采用网络读取，不缓存受保护响应。

### 健康数据

- Health Auto Export JSON v2 和旧格式兼容；
- 支持步数、活动能量、静息能量、Apple 锻炼时间、体重、睡眠和静息心率；
- 支持 kcal、kJ、J 之间的能量换算；
- 支持 kg、lb 等体重单位换算；
- 今日数据严格按上海时区匹配，不再将昨天记录显示为今天；
- 页面回到前台时自动刷新；
- 7 天／30 天趋势和 CSV 导出；
- 健康同步状态中心：今日状态、最后上传时间、数据日期、指标缺失提示和手动刷新；
- 今日步数目标可编辑，保存在当前设备的 `localStorage`。

### 工作日历

- 月份前后切换和全年视图；
- 2026 年法定节假日与调休上班；
- 编辑模式下可逐日设为工作或休息；
- 个人修改、工作日、法定假日、调休、周末和今天使用不同短横线标识；
- 桌面端与移动端统一显示；
- 月度工作日数量实时驱动当月工资；
- 月度排班、请假和加班备注。

### 工资

- 后端固定算法：日薪 275 元、固定扣除 130 元、起征点 5000 元、税率 3%；
- 应发、扣除、计税收入、个税和实发工资实时计算；
- 工资历史、趋势图和 CSV 导出；
- 当前月份可保存，历史月份不可覆盖；
- 当前月工资记录与工作日历不一致时提示更新；
- 取消历史工资纠错和删除，保持历史记录不可修改。

### 工作经历

- 新增、编辑和删除工作经历；
- 记录单位、职位、开始月份、结束月份和工作内容；
- 自动按年月排序；
- 单一时间线视图，取消意义重复的列表视图；
- D1 持久化，支持跨设备读取。

### 安全与可靠性

- Cloudflare Access 保护网页及业务 API；
- 健康上传使用独立 API Key；
- 统一安全响应头；
- API 输入范围、日期格式和字段长度校验；
- D1 备份和恢复脚本；
- 生产依赖和开发依赖已完成高危漏洞修复；
- 自动化测试覆盖访问控制、日历、工资策略和健康数据解析。

2. 全量个人数据备份与恢复：已有命令行 D1 备份流程，但没有网站内导出/恢复界面；

- 记住上次访问页面：单人网站收益不足；
- 工资历史纠错与删除：历史应保持不可修改；
- 列表/时间线双视图：信息重复，只保留时间线；
- 日历备注自动扣款：自由文本无法可靠计算；
- 加班自动汇总：目前没有结构化时长数据；
- 更多健康指标、主题切换和可配置首页：暂时没有明确需求；
- 统一生活时间线：不同数据语义差异过大，暂缓。

## 6. 当前遇到的问题

### 6.1 体重尚未进入 D1

网站接口已经支持体重，但最近检查的 D1 记录中 `weight_kg` 仍为 `null`。这说明 Health Auto Export 尚未实际上传体重数据，而不是网页趋势组件故障。

排查顺序：

1. Apple 健康中允许 Health Auto Export 读取“体重”；
2. Pulse 自动化中选择“体重”；
3. 日期范围设为“今天”或“最近 7 天”；
4. 汇总开启、时间分组为“天”、JSON v2；
5. 重新执行一次手动导出；
6. 在网站“健康 → 同步”中点击“立即刷新”。

仅勾选体重不会立即上传此前添加的数据。

### 6.2 iOS 后台自动同步不稳定

Health Auto Export 无法在 iPhone 锁定时自由读取 HealthKit。快捷指令的“打开健康/健身 App”自动化也曾出现手动可运行、自动不触发的情况。因此不能假定每次打开 App 都一定上传，当前以定时同步、前台手动导出和网站状态中心核验为准。

### 6.3 登录仍以邮箱验证码为主

Cloudflare Access 已经保护网站，但 OTP 邮件偶尔延迟。推荐将 Cloudflare 本身添加为 Identity Provider，限制为当前 Cloudflare 账户成员，并将会话期设为 30 天；不要在应用内自建密码系统。

### 6.4 README 部分内容已过期

README 仍写着“当前演示数据无需数据库”，与当前实际使用 D1 的状态不符。后续应更新 README，避免新维护者误判部署要求。

### 6.5 服务器渲染测试的本地兼容问题

`tests/rendered-html.test.mjs` 在普通 Node 环境中可能因 `cloudflare:` ESM 协议无法加载而失败。API 测试可正常运行；页面最终以 `npm run build` 的 vinext/Cloudflare 构建结果为准。后续可改用 Miniflare/Workers 测试环境，或调整测试以避免直接加载 Cloudflare 专用模块。

## 8. 需要注意的技术限制

### Cloudflare 与运行环境

- Node.js 要求 `>= 22.13.0`；
- 项目使用 vinext，而不是标准 Next.js Node 服务；
- 构建产物使用 Cloudflare Workers ESM 环境；
- Worker 通过 `dist/server/wrangler.json` 的重定向配置部署；
- D1 是 SQLite 语义，不适合依赖传统长事务、复杂并发写或数据库服务器扩展；
- Wrangler 上传偶尔会出现 `fetch failed`，通常自动重试后成功，应以最终 Version ID 为准。

### 认证与密钥

- 业务页面只信任 `pulse.sophier.org` 上 Cloudflare 注入的 `Cf-Access-Jwt-Assertion`；
- `workers.dev` 地址不是正常业务入口；
- 健康上传接口不能使用 Access 网页登录，依赖独立 `X-API-Key`；
- API Key 只能保存在 Cloudflare Secret 和 iPhone 自动化中，不得提交 GitHub或写入文档；
- 不建议再实现一套应用内用户名密码认证。

### 健康数据

- Health Auto Export 的健康读取权限、指标选择和实际导出是三个独立步骤；
- iOS 锁屏和后台调度会影响自动上传时机；
- 同一天数据使用日期唯一记录覆盖更新；
- `0` 可能代表真实零值，也可能代表该次汇总未包含相应指标，不能据此做医学判断；
- 网站只做数据展示，不提供医疗诊断；
- 体重、睡眠和静息心率允许为空；
- 今日判断统一使用 `Asia/Shanghai`。

### 日历与工资

- 当前法定节假日和调休表只维护了 2026 年，进入新年份前必须根据正式通知更新；
- 浏览其他年份时不能假定节假日安排准确；
- 工资算法是用户当前约定的简化规则，不是通用中国个税计算器；
- 固定算法位于后端 `app/api/salary/policy.ts`，前端不得单独维护另一份不同规则；
- 历史工资不可修改，仅上海时区当前月份可以保存；
- 工作日历个人编辑直接影响当月工资计算，修改时需保持确认和撤销路径。

### 前端与 PWA

- 主要页面目前集中在 `app/page.tsx`，继续增长会增加维护成本；较大新功能应拆分组件和 hooks；
- `app/globals.css` 历史样式较多，新样式必须使用组件作用域，避免再次发生移动端旧规则覆盖；
- PWA 图标与 manifest 容易被 iOS 主屏幕缓存，图标修改通常需要版本化文件名并重新安装；
- Service Worker 当前为 network-only，不提供离线数据能力，这是为了避免缓存个人敏感数据；
- 步数目标只保存在当前设备 `localStorage`，不会跨设备同步。
