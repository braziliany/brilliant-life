# 璀璨人生部署与恢复手册

## 1. 新环境部署

### 前置条件

- Node.js 满足 `package.json` 的 engines；
- Git、GitHub CLI、Wrangler 可用；
- 已登录正确的 GitHub 与 Cloudflare 账户；
- Cloudflare Access、D1 和自定义域名仍在正确账户中；
- 健康上传密钥通过 Wrangler secret 管理，不写入仓库。

### 部署流程

```powershell
git clone https://github.com/braziliany/brilliant-life.git
cd brilliant-life
npm install
npm run verify
npx wrangler deploy
```

核对：

- `vite.config.ts` 中数据库 ID 与生产 D1 一致；
- `vite.config.ts` 显式包含 `workers_dev: false` 与 `preview_urls: false`；
- `.openai/hosting.json` 只含逻辑 binding `DB`，不含密钥；
- `HEALTH_INGEST_API_KEY` 已设置为 Worker secret；
- `pulse.sophier.org` 仍受 Cloudflare Access 保护；
- Calendar Widget Service Token 只能访问精确 Widget path；
- Health Ingest 独立 Access Application 与 Health Service Token 只允许精确 `POST /api/health/ingest`；
- Cloudflare API 返回 Worker subdomain `enabled=false`、`previews_enabled=false`，并从独立出口确认 canonical workers.dev 与 Version/Preview URL 无法进入 Worker 业务处理路径。

`npm run verify` 是发布硬门禁，必须整体通过。它覆盖生产构建、领域/API 回归、本地 D1 migration 和本地 Workers HTML；不得只运行其中一部分后发布。

## 2. 数据库迁移

只有 `db/schema.ts` 确实变化时才生成迁移：

```powershell
npm run db:generate
```

必须人工检查新 SQL，不得重新执行已应用迁移。结构变更前先运行 `npm run db:backup`。迁移必须先通过空库和中间 schema 烟雾测试，再经单独审批应用到远端。

### Calendar 实际记录表 0015 的发布顺序

1. 核对获批工作树、Node 22、生产 DB 身份和当前承接流量的 Worker 版本；确认生产具有 0014 基线，且 `calendar_work_records` 尚不存在。
2. 创建迁移前备份，核验 SQL SHA-256，并将真实备份导入隔离本地 D1，按 metadata 比较表、索引、行数和关键快照。备份脚本的导出与 metadata 查询分次进行；若后台写入造成不一致，应重新取得一致备份，不能修改 metadata 掩盖差异。另记录 Time Travel bookmark 和活跃 deployment，不能只使用 versions 列表中的最新编号。
3. 获批后仅执行 `drizzle/0015_romantic_bastion.sql`：`npx wrangler d1 execute DB --config .\dist\server\wrangler.json --remote --file .\drizzle\0015_romantic_bastion.sql`。生成配置的 migration 目录并非 Drizzle SQL 目录，不使用 `migrations apply`，也不重放旧迁移。
4. 确认新表四字段、日期主键和初始空表，旧个人安排、工资快照及其他历史记录保持，再发布新 Worker；新 Calendar、Annual 和 Widget 读取依赖此表，不能倒序发布。
5. 正式部署沿用生成配置，使用 `npx wrangler deploy --keep-vars` 保留已有普通变量；不传入 secrets 文件，不修改 Access、DNS 或 Secrets。发布后验证活跃版本、DB binding、入口保护及业务读取。

0015 报错或网络超时后先只读确认真实状态，不盲目重试，不擅自删除已有表。Worker 回滚保留新增表和记录；旧代码会忽略实际记录，不能称为数据语义等价回滚。数据库恢复仍须单独批准，不能作为默认应用回滚步骤。

### 物品档案 0016 的发布顺序

1. 核对获批分支、远端、代码提交、Node 22 和完整 verify；核实活跃 Worker 及其 `DB` 绑定。生产须已具备 0015 的九张旧业务表，三个 `possession_*` 表尚不存在。只读检查 schema，不以本地 journal 代替生产事实。
2. 用现有备份脚本导出生产 D1，核验 SHA-256，并在独立的本地 D1 恢复。比较九张表、全部显式索引、行数和全部旧记录摘要（包括所有 Salary 历史快照），确认备份与生产读取一致；另记录 Time Travel bookmark。备份 SQL 和私有数据只留在忽略目录，不提交或同步 Obsidian。
3. 在该隔离库试执行 0016 并核对只新增三表和六个索引，旧记录摘要不变。生产仅执行已提交的 `drizzle/0016_possessions_phase1.sql`，使用已核对 DB binding 的生成配置、`d1 execute DB --remote --file`；不执行 `migrations apply` 或重放旧迁移。若结构已存在，先核对是否完整，不能重复执行；若报错或超时，先只读检查状态，不能盲目重试或删表。
4. 迁移后比较新表完整 schema、索引、CHECK 与 RESTRICT 外键，确认三个新表为空、九张旧表和原索引/数据未变，再从同一代码提交重新构建并执行一次 `wrangler deploy --keep-vars`。不改 Access、DNS 或 Secrets。
5. 核对部署版本及 100% 流量、匿名拒绝、Owner 只读页面/API，以及机器边界。合法登录不可用时明确标为 NOT VERIFIED，不提取 Cookie/JWT、不伪造身份、不创建生产验收记录。完成后追加实际发布记录、同步文档并保持 Git 干净；用户确认实机通过即停止相应本地预览。

0016 的代码回滚保留新增表和其中的记录；旧版本会隐藏物品入口，不能用删表替代回滚。整库恢复会覆盖备份后其他领域的新事实，必须另行明确批准，不是默认失败处理。

## 3. 灾难恢复顺序

1. 停止页面编辑和健康自动上传；
2. 记录当前 Worker 版本、D1 database_id 和 Time Travel bookmark；
3. 若生产库仍可读，先运行 `npm run db:backup`；
4. 在独立 D1 中恢复目标备份并通过 `db:verify`；
5. 判断使用 Time Travel 还是 SQL 恢复；
6. 明确批准后才允许生产恢复；
7. 部署已验证的 Worker 版本；
8. 验证 Access、首页、API 和健康上传；
9. 记录恢复时间、备份哈希、Worker 版本与结果。

## 4. 数据恢复验收

- 当前 schema 的业务表存在（Calendar 0015 后九张，物品 0016 后十二张）；
- 当前 schema 的全部索引与备份 metadata 一致；
- 每张表行数与 metadata 一致；
- 已保存工资快照一致，不用当前算法覆盖历史；
- 最新健康日期和来源一致；
- 工作经历按开始年月与 ID 排序一致；
- 网站能读取数据且 Access 仍返回登录跳转；
- 健康上传密钥只在 iPhone 与 Worker secret 中存在。

## 5. Migration 本地烟雾测试

运行 `npm run test:migrations`。测试会验证：

- 空白本地 D1 能按顺序执行全部 migration；
- 带合成旧数据的中间 schema 能升级到最新版本；
- 健康、工资、日历覆盖和职业经历数据升级后保持不变；
- 临时数据库和配置在测试结束后自动删除。

该命令不读取生产备份、不连接远程 D1，也不能替代生产迁移前的真实备份与独立恢复演练。

## 6. Worker 回滚

列出版本：

```powershell
npx wrangler versions list --name pulse-health-dashboard --json
```

回滚只改变 Worker 代码，不自动回滚 D1。若故障包含数据写入，必须分别执行数据库恢复流程，不能假设 Worker 回滚会还原数据。

## 7. 密钥与账户恢复

- Cloudflare、GitHub 和邮箱启用 MFA；
- 健康上传 API Key 泄露或 iPhone 丢失时立即轮换 Worker secret；
- 更新 Health Auto Export 后先手动验证一次上传；
- 不在聊天记录、文档、Git commit、SQL metadata 或截图中保存明文密钥；
- Pulse Dashboard 的人类网页登录仅使用 Cloudflare Access One-time PIN，唯一 Allow 策略为 `Email = questioniar@outlook.com`；应用会话持续时间为 2 weeks（14 天）。
- Pulse 应用关闭 Cloudflare IdP 与即时认证。Cloudflare IdP 仍保留在 Zero Trust 账户层，不再进入 Pulse 的日常登录链路。
- OTP 邮件延迟时先等待并检查垃圾邮件，不要连续重发；仍失败时按 [Cloudflare Access](./Cloudflare%20Access.md) 检查邮箱、应用 IdP、Allow Owner 与 Access 日志，不要修改应用数据库或业务代码。
- Health Auto Export 使用独立 Health Service Token 通过精确 path 的 Access 边界，并继续使用独立 `X-API-Key` 完成 Worker 应用鉴权；不得改为依赖 Cloudflare Account 交互登录或 Calendar Widget Service Token。Finance API 继续保持现有 Access/应用鉴权边界。

## 8. 定期运维

- 每月生成一次 D1 备份；
- 每季度恢复到临时 D1 并记录结果；
- 每次 schema 变更和批量编辑前额外备份；
- 保留至少 3 个时间点和一份加密异地副本；
- 每季度确认 GitHub、Cloudflare、Access 和邮箱的恢复方式仍可用。
